## 3. evsearch E1 の遅れ：原因と直し（6〜14 本目）

- 6 本目：E1 が変更前（`b8`）の 1.039 倍。7 本目は計測窓の 32 スレッドの計測と重なり、ばらつきで判断できなかった。
- 8 本目：反復 1・10・30 回で、遅れは反復によらない固定の分（+76M〜105M サイクル）。`ec2419c` はかえって悪い（1.08 倍）。
- 9 本目：`evtool.hpp` だけ新しくした版（vH）で 1.080 倍。何もしない命令を足した版（p16〜p48）は 1.000 倍だったが、11 本目の map で、この版では `features` が動いていなかったと分かった（この試しは無効）。
- 10 本目：段階ごとのサイクル数で、遅れはほぼすべて学習データの特徴の計算（`features`、+12.5%）。11 本目：`features` と `get_moves` の機械語は同じで、番地が 2,320 バイト動いていた。速さは `features` の 64 バイト内の位置とそろう（48：1.000、16：1.056、0：1.080）。CPU は AMD Ryzen 9 9950X。
- 12 本目：リンカの `/ORDER` は static 関数に効かない（LNK4037）。13 本目：`#pragma code_seg(".text$a1")` で区画に置くと、前に何も置かない形（s0）が b8 と同じ（反復 1 回 1.000、10 回 1.002）。前に 16・48 バイトを置くと 1.07〜1.08 倍に戻る。→ **原因は同じ機械語の置き場所（確かめた）**。s0 の形を `6993cf8` に入れた。
- 14 本目：E1 は C の 0.958 倍（12/12 で C++ が速い）、15 本目：b8 の 0.998 倍。

## 6. E2・E3 の遅れ：原因と直し（16〜21 本目、上位の窓）

調べ方は 3 章と同じ（計測の窓の待機列、論理CPU 30、記録 `runs\evtools2-request\run16.log`〜`run21.log`、台本 `run-evtools3k.ps1`〜`run-evtools3p.ps1`、変種 `runs\evtools3\var2`、変種を作る道具 `make_*.py`）。

- 16 本目（段ごとのサイクル数、`b8` 相当＋計時 対 `b11` 相当＋計時）：
  - E3 の遅れ（+32M）はほぼすべて読み込みの段（+33M）。
  - E2 の遅れ（+47M）は試験の段 +19M、読み込みの段 +9M、特徴 +3M など。
  - map の比べ：`features`・`run_config$omp$1〜7` は `b8` と同じ 64 バイト内の位置。動いたのは `apply_base$omp$1`（0 → 16）、`stable_discs`・`edge_stable`、`apply_teacher$omp$1`、`load` など。MSVC は区画の中の関数を名前の順に並べるので、関数が増減すると後ろが動く。
  - `#pragma code_seg` の区画には、関数の OpenMP の部分（`$omp$n`）も一緒に入る（変種 g1 の map で確かめた）。
- 17 本目（直しの候補 f1）：
  - E2 は**試験の位置の教師の評価を手数ごとに 1 回だけ計算する**（`teacher_test`。それまでは構成ごとに計算し直していた）ことで、`b8` の 0.861 倍。
  - E3 は `apply_base` と `run_config` を `b8` と同じ 64 バイト内の位置に固定しても 1.029 倍。
  - 出力は E1〜E4 とも `b8` と同じ。
- 18 本目：
  - 読み込みの段を分けて測ると、E3 の遅れは `apply_base` の中（+21.8M）。データの読み込みは同じ。
  - `load` を `b8` と同じ 64 バイト内の位置（48）に固定した f2 で、E2 は 0.822 倍。
- 19 本目：`apply_base` が 4 KiB の境目をまたがない位置（f4・f5、0x2010）でも E3 は 1.05 倍。前の窓のアセンブリの一覧（`asm-ev-main`・`asm-ev-cb0`）では、`apply_base` と `apply_base$omp$1` の機械語は `b8` と同じ。
- 20・21 本目：`apply_base$omp$1` を **4 KiB のページの先頭**（f6：0x1000 で `b8` と同じ番地、f7a・f7b：0x2000）に置くと、E3 は `b8` の 0.996〜1.005 倍（2 回の計測で確かめた）。原因は、機械語の置き場所の 4 KiB のページの中の位置（番地の下 12 ビット）と考える（見立て：命令のキャッシュのどの組に入るかが決まり、ほかの熱いコードとのぶつかり方が変わる）。
  - E1・E4 は、どの変種も `b8` の ±1.5% の中で、回ごとに揺れる（同じ f2 で 1.002〜1.016）。ほかの作業が動き始めてからは、1% の違いは見分けられない。
  - `run_config`・`load` も f2 と同じページの中の位置に保った f8（3.8KB の詰め物）は、f7a と見分けられなかった。
- **直し（f7a の形、`evsearch.cpp` の「Places of the hot code」）**：
  - コードの先頭から、`.text$a1`（数値の特徴と `features()`、3,728 バイト）、詰め物 a（368 バイト）、`.text$a3`（`apply_base`、ページの先頭）、詰め物 b（48）、`.text$a5`（`run_config`）、詰め物 c（48）、`.text$a7`（`load`）。
  - 試験の位置の教師の評価は `teacher_test` で 1 回だけ計算する。そのための `double` の配列は、試験のデータでは使わない `c`・`t` の配列（合わせて容量×8 バイト）を先に返してから取るので、メモリは増えない。
  - `build-evtools.ps1` は evsearch を map つきでリンクし、`apply_base$omp$1`（4096 の倍数）、`features`（64 で割って 48）、`run_config$omp$1`（0）、`load`（48）の位置を確かめる。ずれていれば警告に数える（前のコードの大きさが変わったとき）。
  - 詰め物の大きさ：nop の数＋9 バイト（書き込みと `ret 0`）を 16 に切り上げたもの（17〜21 本目の map で確かめた）。
  - evsearch の実行ファイル：`b8` 233,984 → `b11` 241,152 → f7a 241,664 バイト（直しで +512）。
