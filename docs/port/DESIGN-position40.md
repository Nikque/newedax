# 設計案：book の局面を 48 バイトから 40 バイトに（2026-10-16、未実装）

書いたのは Claude Opus 5.5。**（書いた時点では）実装していない。** 実装は 7 章。

## 1. ねらい

主な使い方は `book deviate`（6.6 億局面の book）。book のメモリのほとんどは局面（`Position`、64ビットで 48 バイト）なので、40 バイトにすれば局面の分が約 17% 減る（6.6 億局面で約 5.3GB、見積もり）。book を歩く処理（deviate の選択、negamax、link）も、読むメモリが減る分だけ速くなる見込み（見立て、測っていない）。**ファイルの形は変えない**（保存するバイトは同じ）。

## 2. 今の 48 バイトの内訳（`book.cpp` 126〜143 行、確かめた）

| 項目 | バイト |
|---|---|
| `board`（盤面） | 16 |
| `links`（4本までの Link を埋め込むか、5本以上の配列へのポインタ） | 8 |
| `n_wins`・`n_draws`・`n_losses`・`n_lines`（各 32 ビット） | 16 |
| `score`（3）・`leaf`（2）・`n_link`・`level`・`state` | 8 |

4つの数は、`book store`・`book learn`・数え直しで集計され、ファイルに 32 ビットで保存される（集計は `UINT_MAX` で頭打ち）。

## 3. 値の分布（確かめた。`base12.dat`、83,274 局面）

- すべての局面で、4つのうちどれかが 0 でない。
- 最大値が 255 を超える局面：810（1%）。65,534 を超える局面：4（0.005%）。最大 733,028。
- 大きな値は根に近い局面（その下の棋譜の数）に限られる。6.6 億局面の book でも、65,534 を超える局面はごく一部と見込む（見立て。実bookは使わない）。

## 4. 案

- 4つの数を各 16 ビット（計 8 バイト）にする。どれかが 65,534 を超える局面は、16 ビットの欄を「別の表にある」印（65,535）にし、本当の値（4 × 32 ビット）を book ごとの表（`boost::unordered_flat_map<盤面, 4つの数>`）に置く。局面は 40 バイトになる（静的な検査で守る）。
- 数を読む・書くのは、すべて関数を通す（`position_counts(book, p)`・`position_set_counts(book, p, ...)`）。今の直接の読み書き（book.cpp 55 か所、libedax.cpp 14 か所）を置き換える。
- **難しい所**（この案で一番気をつける所）
  1. book の外の一時的な局面（`position_read` で読んだ `p` を `book_add` で写す、merge の一時変数など）。一時的な局面は 32 ビットの4つの数を持つ別の型（例：`PositionRecord`）にし、book に入れる所（`book_add`）で 16 ビットと表に分ける。読む・保存する所（`position_read`・`position_write`）は `PositionRecord` を使う。
  2. book から book への写し（merge、subtree、import、`book_grow_buckets` のような同じ book の中の移動）。同じ book の中の移動は、表のキーが盤面なので何もしなくてよい。別の book への写しは、必ず関数を通す。
  3. 局面を消す所（`book_remove_at`、prune、`book_free`）で表の項目も消す。
  4. 並列の処理（negamax・link・correct などの worker）が数を書く所。表への書き込みは、局面の数が 65,534 を超えるときだけで、まれ。表に書く所はロックで守る。
- 検査：14 suite の book（試験 A と同じ）が保存日時以外のバイトまで記録と一致すること。数が 65,534 を超える局面を含む book（`base12.dat` に4つある）で、load → save のバイトが一致すること。API 試験 204 件。

## 5. 速さ・メモリの見立て

- メモリ：局面 1 つ 8 バイト減。表は 65,534 を超える局面だけ（1 項目 約 40 バイト）。
- 速さ：数を読む所に「印か」の判定が1つ入る（数を使うのは集計と保存だけで、探索の中ではない）。book を歩く処理は、メモリが減る分だけ速くなる見込み。
- 悪くなる条件：数の大きい局面が非常に多い book（例：65,534 を超える局面が 2 割以上）では、表の分だけメモリが増え得る（1 局面あたり約 40 − 8 = 32 バイト増えるのは、その局面だけ）。
